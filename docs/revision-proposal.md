- Standard Challenge は1日に複数回開催されることを前提にする。同じ大会かどうかは MTGO の大会番号で判定する。

### B3 の調査結果

- Petrified Hamlet / Witherbloom Charm（SOS）: 8/13 の辞書更新の時点で、日本語版が Scryfall に未登録でした。期限切れのキャッシュは次回の辞書更新で再取得されます。

- Twinmaw Stormbrood: Scryfall の日本語版で、クリーチャー側の面の名前が英語のままになっています（出来事側は翻訳済み）。Scryfall 側のデータが直るまで英語表示になります。

## 2. 確認できた不具合（優先度：高）

### B1. 同じイベントが2回表示される
- **根拠**: `index.json` の 2026-09-23 に `standard-challenge-16-2026-09-1412854542` と `standard-challenge-16-2026-09-2312854542` の2件があり、デッキの内容は完全に同じでした。MTGO 側で URL の日付部分が変わり、同じ大会が別のイベントとして登録されています。
- **原因**: `eventIdFromUrl()`（`scripts/lib/event-rules.mjs`）がイベントIDを URL の slug 全体から作っているため。
- **修正案**: slug の末尾にある MTGO の大会番号（`12854542`）を同一判定に使う。`build-public-index.mjs` で同じ番号のイベントは新しい1件だけを残す。既存の JSON は削除しない（CLAUDE.md のルール）ので、公開 index から除外する形で対応します。

### B2. 日本語名にふりがなが混ざる（33種類）
- **根拠**: `card-search-index.json` の33種類で、`無（む）効（こう）`、`繁（はん）殖（しょく）池（いけ）`、`光（ひかり）に導（みちび）かれし者（もの）、ハリーヤ` のようなルビ付きの名前になっています。EOE と TRK の日本語版で発生しています。
- **原因**: Scryfall の `printed_name` にルビが含まれているセットがあり、その文字列をそのまま辞書に入れているため。
- **修正案**: 辞書を作る段階（`getJapaneseName`）で `漢字（ひらがな）` の形をした部分のルビだけを取り除く。検索用の正規化キーも同じ処理を通す。翻訳処理の変更になりますが、表示上の不具合がはっきりしているため CLAUDE.md の「明確な不具合」に当たると判断しています。

### B3. よく使われるカードが未翻訳になっている
- **根拠**: 直近10日の未翻訳は91行で、上位は Clarion Conqueror（23行）、Twinmaw Stormbrood（13行）、Petrified Hamlet（11行）、Witherbloom Charm（8行）です。Clarion Conqueror の `detailUrl` は日本語版（`/tdm/5/ja/`）を指していますが、`nameJa` は `null` でした。Twinmaw Stormbrood の URL には日本語名が含まれています。
- **原因の候補**:
  - 2面カード（Omen などの layout）で片方の面しか名前が取れないと、`status: partial` になり `nameJa: null` を返している。
  - 日本語版が見つからなかった結果のキャッシュ（`scryfall-ja-cache.json`）が期限切れ前で、再取得されていない。
- **修正案**: 上記4枚で `diagnoseCardNames` を実行して原因を確定してから直します。手動補正（`manual-overrides.json`）での対処はしません。

### B4. カード検索の結果が選択中の1日分しか出ない
- **根拠**: `App.tsx` が起動時に `selectedDate` を必ず1日に設定し、日付を解除する手段がありません。`EventList` はその日付で絞り込みます。一方、検索候補には10日分の「◯デッキ」が表示されるため、候補で見た件数と結果の件数が合いません。
- **修正案**: 日付の選択肢に「全期間（10日）」を追加し、カードかセットで絞り込んだときは自動で全期間に切り替える。

### B5. スマホ表示のレイアウト
- 日付見出しの固定位置が `sticky top-[120px]` に固定されていますが、`FilterBar` の高さは画面幅によって変わります。そのため、スマホでは見出しがフィルタの下に隠れます。
- スマホでは `FilterBar`（日付・種別・表示言語・セット・検索）がすべて固定表示されるため、画面の高さの約4割を占めます。

### B6. イベントJSONを毎回取得し直している
- `useEventData` は `cache: 'no-store'` を指定して、イベントカードごとに取得します。デッキ詳細を開くと同じ JSON をもう一度取得します。1イベントは約100KBで、10日分では約1.8MBをページを開くたびに取得しています。
- **修正案**: 取得したイベントをメモリにキャッシュする（モジュールレベルの `Map`）。`no-store` は `index.json` だけに付け、イベントJSONにはファイル名にバージョンを付けるか、通常の HTTP キャッシュを使う。

### 参考: セットでの絞り込みで再録カードの影響が大きい
- TRK（Star Trek）は、ショックランドの再録により105デッキに一致します。`Overgrown Tomb` の `primarySetCode` が TRK になっているためです。この挙動は README にある仕様どおりですが、「新しいセットのカードがどれだけ使われているか」を知りたい場合には役に立ちません。
- **修正案（任意）**: セットで絞り込むときに「このセットで初めて収録されたカードだけ」を選べるオプションを追加する。

## 3. 構成の見直し

### A1. `public/data` を生成物にする（優先度：中、効果が大きい）
- 現状: `data/events` と `public/data/events` に同じ JSON を2回書いています。どちらも Git にコミットしており、さらに10日より前のイベント（224件中約200件）もデプロイしています。`docs/conflict-prevention.md` と `pr-conflict-guard.yml` は、この重複が原因で起きるコンフリクトへの対策として作られたものです。
- 提案:
  1. 保存用データは `data/` だけに置く（`data/events` は削除しない）。
  2. `build:index` で `public/data/` に **直近10日分のイベントだけ** をコピーし、`public/data/` は `.gitignore` に追加する。Actions ではビルドの前に `build:index` を実行する。
  3. 変更があったかどうかは `public/data` の差分ではなく `data/` の差分で判定する。
- 効果: リポジトリの増え方が半分ほどになり、デプロイするファイルは約24MBから約2MBになります。生成物どうしのコンフリクトも構造上ほぼ起きなくなります。
- 注意: CLAUDE.md の「変更がない場合のコミット・デプロイ判定は `public/data` の差分で行う」という記述を更新する必要があります。

### A2. 生HTML（`data/raw/events`、43MB）の扱い
- 1日3回の定期取得で増え続けます。再解析に必要なのは、パーサーを修正したときだけです。
- 提案: 次のどちらかを選ぶ。
  - (a) 完了したイベントは gzip で保存する（`.html.gz`）。
  - (b) Git の管理対象から外し、Actions の artifact（保存期間90日）に保存する。テスト用のフィクスチャは `tests/fixtures/` に必要な分だけ置く。

### A3. イベントの同一判定（B1 の恒久対策）
- `state/events.json` のキーに MTGO の大会番号（数字）を追加し、URL の slug が変わっても同じイベントとして扱う。

### A4. 不要になったものの整理
- `@supabase/supabase-js` はどこからも使われていないため、依存から削除する。
- `package.json` の `name` が `vite-react-typescript-starter` のままなので、`mtgo-standard-deck-survey` に変更する。
- `.bolt/` は Bolt で作っていた頃の名残。今後 Bolt を使わないなら削除する。
- ワークフローの Node のバージョンが揃っていない（20 と 24）。どちらかに統一する。

## 4. UI の刷新案

テーマ（ダークトーン、`primary` / `warning` などのカラートークン、Noto Sans JP）と既存のコンポーネントはそのまま使い、**情報の構成と見せ方** を中心に見直します。

### 4.1 情報の構成

現在の表示は「ヘッダーの状態バッジ」「UpdateStatus」「ProcessingStatusPanel」の3か所で取得状態を出しており、閲覧者にとって主役のデッキ一覧より目立っています。

```
┌ Header ─────────────────────────────────────────────┐
│ MTGO Standard Results     [デッキ][カード][取得状況]  ●更新 9/30 22:05 │
└─────────────────────────────────────────────────────┘
  デッキ   : 期間（全期間 / 日付別）× 種別 × カード × セットで絞り込んだデッキ一覧（メイン画面）
  カード   : 10日間の採用ランキング（新規、§5 F1）
  取得状況 : 現在の ProcessingStatusPanel と UpdateStatus を統合したページ
```

- ヘッダーの状態表示は小さな丸1つと最終更新日時だけにし、詳しい内容は「取得状況」タブに移す。
- タブの状態は URL の hash（`#/decks?date=…&card=…&deck=…`）に保存する。GitHub Pages のサブパスで公開していても動作します。

### 4.2 デッキ一覧

```
PC
┌ フィルタ（固定） ───────────────────────────────────────────┐
│ [全期間][9/30][9/29]…  [すべて|Challenge|League]  [セット▾]  🔍カード名 │
│ 選択中: 鳴り響く征服者 ×   表示: 日本語|日+英|英                        │
└──────────────────────────────────────────────────────────┘
 9月29日(火)
 ┌ Standard Challenge 16 · 19:30 · 8デッキ ───────────── 元ページ ┐
 │ 1位  PlayerA   ⚪🔵  光に導かれし者、ハリーヤ / 鳴り響く征服者 …  │
 │ 2位  PlayerB   ⚫🟢  …                                  4枚 ◀検索一致 │
 └──────────────────────────────────────────────────────────┘
```

- **デッキ行に色と主要カードを表示する**: 土地以外で枚数の多いカード2〜3枚と、色（カードの色情報を辞書から付ける）を並べ、プレイヤー名だけの行より見比べやすくします。アーキタイプの自動判定は README で対象外とされているため、ここでは行いません。
- 同じ日にある複数の League（例: 9/29 の `…11015` と `…11129`）は、1枚の「League 5-0」カードにまとめて表示する。
- 日付の見出しは `FilterBar` の実際の高さに合わせて固定位置を決める（`ResizeObserver` で計測し CSS 変数に入れる）。B5 の対策です。

### 4.3 スマホ

- 固定表示するのは「検索ボックス」と「期間・種別」の1行だけにし、表示言語とセットは「絞り込み」ボタンから開くボトムシートに移す。
- デッキ詳細はメインとサイドをタブで切り替える（今は縦に長く並んでいます）。
- デッキ詳細に「前のデッキ / 次のデッキ」ボタンを付け、左右スワイプでも移動できるようにする。

### 4.4 デッキ詳細

- 外部 API を呼ばずに、手持ちのデータからマナカーブ（点数で見たマナ・コスト別の枚数）とタイプ別の枚数を出す。辞書に `cmc` を追加する必要があります。
- コピーボタンを目立たせる（今は小さな文字リンクなので気づきにくい）。
- URL でデッキを直接開けるようにし、共有ボタンを付ける。
